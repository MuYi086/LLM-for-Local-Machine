# 开发工作流

本文描述本仓库的需求分级、不确定事项处理、验证纪律与规格回写方式，对标参考项目的
spec-driven 工作流并适配后端模型服务仓库。协作原则与技术约束以根目录
[AGENTS.md](../AGENTS.md) 为准；规格体系结构见 [OpenSpec 说明](../openspec/README.md)。

## 选择工作方式

| 类型 | 做法 |
| --- | --- |
| 局部修复、文案、配置微调 | 直接修改并验证，不建 change。 |
| 新增模型 API、修改服务合同或端口 | 建立 OpenSpec change（proposal/design/tasks/verification），实现前先核对清单事实。 |
| 启动编排、GPU 锁、隔离恢复等高风险机制变更 | 规格先行：先确认关键规则与副作用，按风险制定验收方案再实施。 |

以实际影响判断，同一需求可以同时包含可独立推进的实现和被外部事实阻塞的部分。
设计/计划是实施依据；已确认的行为写入主规格；未决事项单独记录，不混入基线。

本仓库没有前端 Mock 环节，与接口未定场景对应的机制是：上游模型行为未确认时，
以清单与实测报告为已确认来源；不得用合成响应冒充真实模型验证结果。

## 不确定事项

| 状态 | 处理 |
| --- | --- |
| 已确认 | 记录来源（代码、清单、实测报告、上游文档），作为实现与验收依据。 |
| 临时假设 | 标记假设及影响，实现保持可调整，不写入主规格。 |
| 待对齐 | 记录责任方与临时处理，推进无依赖的任务。 |
| 硬阻塞 | 暂停依赖该决定的任务；不自行编造模型能力、上游契约或硬件行为。 |

需要跟踪时在当前 change 的 verification.md 中使用下表；小改动无需强制记录。

| 事项 | 状态 | 依据 / 责任方 | 临时处理 | 影响 / 确认结果 |
| --- | --- | --- | --- | --- |
| 示例：上游响应字段 | 待对齐 | 上游文档 | 按现有字段实现 | 联调时核对 |

确认后记录结果、来源和日期，并同步受影响的文档、清单与规格。

## 验证与收敛

1. **静态核对**：`bash -n start.sh`、Ruff check/format、能力清单校验
   （`scripts/localai/validate_capabilities.py`）、服务口径校验
   （`scripts/check_service_inventory.py`）。
2. **无模型回归**：`uv run --project qa --locked python -m unittest discover -s tests -v`；
   测试不下载权重、不依赖 CUDA、不调用真实模型。
3. **真实模型验证**：单独串行执行（音频样例 `tests/audio_cpp/generate_examples.py`），输出写入运行数据目录。

以上三层 MUST 分开记录：无模型回归通过不代表真实模型验证完成；无法完成的真实模型验证
明确列为未完成，不通过勾选或措辞掩盖。行为或契约变化后同步受影响的清单、
README/AGENTS 口径与对应主规格。

## 归档

- change 的全部任务与验证核对完成后，把目录移入 `openspec/changes/archive/`，
  同步主规格与 [coverage.md](../openspec/coverage.md)。
- 服务口径（端口、路由、数量声明）由 `scripts/check_service_inventory.py` 在质量门禁中兜底；
  归档后如果该工具失败，说明文档同步不完整，不得先归档后补文档。
- 历史资料（task*.md、reports/、docs/superpowers/、.superpowers/sdd/）只记录当时状态，
  不据此推断当前接口；需要历史决策时引用对应归档 change。

## 经验沉淀

处理复杂任务后，把「已验证且可复用」的结论沉淀到
[项目经验索引](agent-memory/index.md)：每条注明来源（报告、issue、实测记录）与日期；
不保存敏感信息、机器专用路径或未确认假设。检索经验后仍需对照当前源码核实。
