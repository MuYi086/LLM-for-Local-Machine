# 空间音频技术方案查询

> 用途：供本地 Codex 结合 `TTS-and-VoiceDesign` 与 `TTS-Studio-WebUI` 渐进落地 Steam Audio 空间音频能力。  
> 结论：**正式空间渲染引擎选择 Steam Audio；不采用依赖 DAW、VST、Unity、Unreal 或 GUI 手工调参的方案。**  
> 调研与仓库核对时间：2026-08-23（Asia/Singapore）。

## 1. 文档依据与适用范围

本方案综合以下三类信息：

1. [空间音频方案讨论记录](https://chatgpt.com/share/6a8aeba9-61f0-83ec-b375-cf7619abd338)：已比较 Steam Audio、Google OBR、3D Tune-In、IEM、Omniphony 等方案；用户实际试听后确认 Steam Audio 的主观效果优于 Google OBR，并最终选择 Steam Audio。
2. [`MuYi086/TTS-and-VoiceDesign`](https://github.com/MuYi086/TTS-and-VoiceDesign)：核对快照为提交 [`5cf2d60`](https://github.com/MuYi086/TTS-and-VoiceDesign/commit/5cf2d60fabb73db264572dc97d6751b8de3b6b1c)。

本方案只规划空间导演、空间渲染、混音与导出链路，不替换已有 TTS、VoiceDesign、SoundEffect、BGM、Step-Audio-EditX 或工程导入导出能力。

如果本地仓库已经晚于上述提交，Codex 必须先阅读最新 `README.md`、`AGENTS.md`、`git status --short` 和相关源码，再把本文当作目标架构，而不是机械覆盖新代码。

## 2. 最终技术决策

| 决策项 | 结论 |
| --- | --- |
| 正式渲染引擎 | Steam Audio C API |
| 输出格式 | 48 kHz 双声道 Binaural WAV，母带后可编码 MP3 |
| 主要收听设备 | 普通耳机；不要求 Dolby Atmos 设备 |
| 自动化方式 | LLM 输出语义空间 DSL，确定性脚本编译为坐标/轨迹，C++ CLI 批量渲染 |
| 集成位置 | `TTS-and-VoiceDesign` 的 8300 控制面；不新增 GPU 模型服务端口 |
| GPU 策略 | 首版使用 CPU 内置射线追踪或 Embree；不占用 TTS 共用 GPU 锁 |
| WebUI 定位 | 生成/编辑语义空间计划、近似预览、打包对象音频；不承担最终 HRTF DSP |
| 第一版能力 | HRTF、方向、距离、空气吸收、静态与简单移动轨迹 |
| 第二版能力 | 房间反射与 Reverb（混响） |
| 第三版能力 | Occlusion（遮挡）与 Transmission（穿透） |
| 明确排除 | DAW、VST、Unity/Unreal、人工拖坐标、人工调旋钮、逐段手工后期 |

选择 Steam Audio 的原因不是它最容易接入，而是它最符合悬疑/恐怖有声内容的最终听感目标：HRTF 负责前后、上下与环绕定位，Direct Effect 可处理距离和空气吸收，场景模拟还能进一步支持门后说话、隔墙声音、走廊反射和房间混响。

Steam Audio 当前仓库采用 Apache-2.0，最新 Release 为 4.8.1，并提供 Windows、Linux 等平台支持。官方 C API 文档确认每个声源可维护独立 `IPLBinauralEffect`，可加载内置或 SOFA HRTF；移动声源适合使用 Bilinear interpolation（双线性插值）以减少方向切换突变。

官方资料：

- [Steam Audio GitHub 与许可证](https://github.com/ValveSoftware/steam-audio)
- [Steam Audio C API Getting Started](https://valvesoftware.github.io/steam-audio/doc/capi/getting-started.html)
- [Steam Audio C API Programmer's Guide](https://valvesoftware.github.io/steam-audio/doc/capi/guide.html)
- [Steam Audio Simulation API](https://valvesoftware.github.io/steam-audio/doc/capi/simulation.html)
- [Steam Audio Build Instructions](https://valvesoftware.github.io/steam-audio/doc/capi/build-instructions.html)
- [官方 `sample_binaural.cpp`](https://github.com/ValveSoftware/steam-audio/blob/master/core/src/samples/sample_binaural.cpp)

> 注意：官方 `sample_binaural.cpp` 只是固定方向、RAW 音频、Nearest HRTF 的最小示例，还会忽略不足一帧的尾部数据。它可以作为 API 学习入口，**不能直接当作生产 CLI**。生产实现必须补齐 WAV/PCM I/O、尾帧补零与裁剪、动态轨迹、错误处理、资源释放、批量混音和自动测试。

## 3. 两个项目的当前真实状态

### 3.1 `TTS-and-VoiceDesign`

当前 8300 控制面已经存在：

- [`main/main.py`](https://github.com/MuYi086/TTS-and-VoiceDesign/blob/main/main/main.py) 中的 `POST /v1/audio/export`；
- [`main/spatial_audio.py`](https://github.com/MuYi086/TTS-and-VoiceDesign/blob/main/main/spatial_audio.py)；
- [`tests/test_spatial_audio_export.py`](https://github.com/MuYi086/TTS-and-VoiceDesign/blob/main/tests/test_spatial_audio_export.py)。

现有链路为：

```text
浏览器已经混好的双声道 WAV
  → FFmpeg SoXR 重采样到 48 kHz
  → standard / balanced / immersive 滤镜
  → 双遍 EBU R128 loudnorm
  → 24-bit WAV 或 192 kbps MP3
```

其中 `balanced` / `immersive` 使用 Side-only Haas、`aecho`、延迟、低通和湿声混合扩大耳机空间宽度。它有以下优点：

- 已有稳定的上传、超时、临时文件清理和响应后清理；
- 已有 48 kHz、响度归一化与 WAV/MP3 编码；
- CPU 执行，不占用 GPU 锁；
- 已有无模型单元测试。

但它不是 Steam Audio，也不是真正的对象级 HRTF：

- 输入已经是总线混音，后端无法知道哪一段是旁白、角色、脚步、敲门或 BGM；
- 无法为单独声源计算前后、上下或移动方向；
- 无法做真实的场景几何遮挡、穿透和物理反射；
- Haas 和固定延迟只能增加宽度，不能替代 HRTF 的前后/高度频谱线索。

结论：**保留它的上传、清理、loudnorm 和编码基础设施；逐步把“伪空间滤镜”从正式 Steam 导出路径移除。**

### 3.2 `TTS-Studio-WebUI`

当前项目不是 npm/Vite/Vue 工程，而是无构建步骤的静态页面：

- 运行入口为根目录 [`index.html`](https://github.com/MuYi086/TTS-Studio-WebUI/blob/main/index.html)；
- Vue 3、Tailwind CSS 等通过 CDN 加载；
- `webUI/` 已废弃，不应向其中新增功能；
- 本地使用 `python3 -m http.server 5173` 启动。

已有空间相关代码：

- [`js/spatial-timeline.js`](https://github.com/MuYi086/TTS-Studio-WebUI/blob/main/js/spatial-timeline.js)：根据角色和自然语言关键词生成声像、距离增益、低通和延迟反射曲线；
- [`js/spatial-audio-client.js`](https://github.com/MuYi086/TTS-Studio-WebUI/blob/main/js/spatial-audio-client.js)：把浏览器混好的 WAV 上传到 8300；
- [`js/spatial-timeline.test.js`](https://github.com/MuYi086/TTS-Studio-WebUI/blob/main/js/spatial-timeline.test.js)：验证角色锚点、左右移动和距离变化；
- `index.html` 中的离线导出会在对象还独立时调用 `StereoPannerNode`、`GainNode`、`BiquadFilterNode` 和两个延迟反射 tap，然后再把总线传给后端。

已有工程协议约束：

- 工程信封仍是 `kind: "llm-local-project"`、`schemaVersion: 4`；
- 时间轴块只有 `dialogue` 与 `bgm`；
- SoundEffect 计划位于 `dialogue.sfx_plan`，每行最多两项；
- 二进制资产存于浏览器 IndexedDB 的 `LLMLocalBackendDB`；
- `audioAssetKey` 是 IndexedDB 稳定键，不是服务端文件路径；
- 兼容逻辑必须集中在 `js/project-storage.js`，不能在模板里再复制一套 Schema。

### 3.3 当前实现的核心冲突

当前 `balanced` / `immersive` 导出会出现两层近似空间处理：

```text
对象级 Web Audio 声像/低通/延迟反射
  → 混成双声道
  → 后端 Side-only Haas/aecho
  → loudnorm
```

如果再直接把这个双声道总线交给 Steam Audio，会产生三重处理，容易导致：

- 声像变虚、相位异常或定位不稳定；
- 对白中心发散；
- 早期反射重复；
- 单声道兼容下降；
- Steam Audio 无法恢复已经丢失的对象边界。

因此必须遵守以下红线：

> **最终 Steam Audio 渲染必须接收尚未进行声像、Haas、房间反射和总线混合的对象音频。Web Audio 近似处理只能用于低成本预览或旧版兼容，不能进入正式 Steam Audio 输入。**

## 4. 目标架构

```text
小说/剧本
  → LLM 剧本导演层
  → 角色、情绪、SFX、BGM 计划
  → TTS / SoundEffect / BGM 生成
  → LLM SpatialDirector（只输出语义 DSL）
  → Spatial Compiler（确定性规则、校验、坐标和轨迹）
  → Render Manifest + 独立音频对象
  → Steam Audio C++ Renderer
  → 48 kHz Binaural Stereo pre-master
  → 现有 FFmpeg 双遍 loudnorm / 编码
  → WAV / MP3
```

职责边界：

| 模块 | 负责 | 不负责 |
| --- | --- | --- |
| LLM SpatialDirector | 从剧情语义选择位置、距离、移动、遮挡、房间标签 | 不输出任意 DSP 参数，不直接处理音频 |
| Spatial Compiler | 校验 DSL，映射到坐标、轨迹、Steam 参数与降级策略 | 不调用 LLM，不生成内容 |
| WebUI | 编辑计划、收集 IndexedDB Blob、近似预览、提交任务 | 不做最终 HRTF/物理声学 |
| 8300 控制面 | 上传治理、Manifest 校验、FFmpeg 预处理、调用 CLI、清理、母带 | 不加载 TTS 模型，不获取 GPU 锁 |
| C++ Renderer | Steam Audio 上下文、每源 Effect、逐帧轨迹、场景模拟、双声道混合 | 不理解小说文本，不读取浏览器 Schema |
| FFmpeg Mastering | 48 kHz、EBU R128、true peak、WAV/MP3 编码 | 不再次添加 Haas/声像/房间反射 |

## 5. 语义空间 DSL 设计

### 5.1 为什么 LLM 不应直接输出 `x/y/z`

本地 Qwen 或云端 LLM 直接生成三维坐标容易出现：

- 同一角色前后句位置跳变；
- “右后方”与实际坐标轴相反；
- 距离、响度和房间关系相互矛盾；
- 输出超范围数值；
- 不同模型、不同 Prompt 生成不可复现结果。

正确做法是让 LLM 只选择有限枚举，再由脚本确定性映射。

### 5.2 建议的对象级 DSL

```json
{
  "version": "1.0",
  "scene": {
    "room": "narrow_corridor",
    "listener_pose": "center_forward",
    "acoustic_quality": "balanced"
  },
  "sources": [
    {
      "id": "dialogue_line_014",
      "kind": "dialogue",
      "asset_id": "line_audio_014",
      "start_ms": 8320,
      "trim_start_ms": 0,
      "duration_ms": 2180,
      "gain_db": -2.0,
      "spatial": {
        "mode": "point",
        "location": "rear_right",
        "distance": "near",
        "movement": "approaching",
        "occlusion": "wooden_door",
        "spatial_blend": "strong"
      }
    }
  ]
}
```

首版枚举建议：

```text
kind:
  narrator | dialogue | sfx | ambience | bgm

mode:
  dry_center | point | diffuse | preserve_stereo

location:
  front_center | front_left | front_right
  side_left | side_right
  rear_left | rear_center | rear_right
  above_front | above_rear | below_front

distance:
  intimate | near | conversational | mid | far

movement:
  static | approaching | receding
  left_to_right | right_to_left
  front_to_rear | rear_to_front
  rising | falling

occlusion:
  none | wooden_door | solid_door
  drywall | concrete_wall | floor_ceiling

room:
  dry_studio | bedroom | living_room
  narrow_corridor | stairwell | basement
  warehouse | cave | outdoor_open

spatial_blend:
  subtle | medium | strong | full
```

### 5.3 确定性映射基线

Steam Audio 监听者坐标建议固定：

```text
right = +X
up    = +Y
ahead = -Z
listener position = (0, 0, 0)
```

距离映射建议从保守值开始：

| DSL | 米 | 典型用途 |
| --- | ---: | --- |
| `intimate` | 0.25 | 贴耳低语，仅用于少量关键事件 |
| `near` | 0.60 | 身边低声、近距离脚步 |
| `conversational` | 1.50 | 普通对话 |
| `mid` | 3.00 | 房间另一侧、近走廊 |
| `far` | 8.00 | 走廊尽头、楼上、远处惨叫 |

方向映射由单位方向向量乘距离得到。例如：

| DSL | 单位方向（约） |
| --- | --- |
| `front_center` | `(0.00, 0.00, -1.00)` |
| `front_left` | `(-0.71, 0.00, -0.71)` |
| `side_right` | `(1.00, 0.00, 0.00)` |
| `rear_right` | `(0.71, 0.00, 0.71)` |
| `above_rear` | `(0.00, 0.71, 0.71)` |

移动轨迹应使用起点与终点语义插值，不允许 LLM 输出每帧坐标。首版采用线性位置插值；后续可加入 ease-in/ease-out，但必须保证每次渲染确定一致。

### 5.4 内容分层策略

10–20 分钟有声内容不能让每句话都强烈移动，否则会产生听觉疲劳。

| 声音层 | 默认策略 | 建议空间强度 |
| --- | --- | --- |
| 旁白 | 前方中心、基本固定、保留大量 dry | `subtle`，约 10%–25% spatial blend |
| 普通角色 | 前方左右小范围稳定锚点 | `medium`，约 30%–55% |
| 关键角色动作 | 依据剧情方向和距离变化 | `strong`，约 60%–85% |
| 剧情 SFX | 允许前后、上下、大范围移动 | `full` 或 `strong` |
| Ambience | 优先 diffuse/Ambisonics 或保留立体声床 | 不当成单一点声源 |
| BGM | 保持稳定立体声，不跟随角色移动 | `preserve_stereo` |

Steam Audio 的 `spatialBlend` 可在空间化与原声之间混合，正好适合保持旁白清晰度。不要为了“听出效果”把旁白全部设成 100% HRTF。

## 6. Render Manifest 与接口合同

### 6.1 C++ CLI 合同

PoC 单文件接口：

```bash
steam-audio-render \
  --input samples/whisper.wav \
  --output out/whisper_spatial.wav \
  --position "0.42,0.0,0.42" \
  --listener "0,0,0" \
  --sample-rate 48000 \
  --hrtf default \
  --interpolation bilinear
```

生产批量接口：

```bash
steam-audio-render \
  --manifest runtime/render-manifest.json \
  --assets-dir runtime/assets \
  --output runtime/pre-master.wav
```

CLI 退出码：

| 退出码 | 含义 |
| ---: | --- |
| `0` | 成功 |
| `2` | 参数或 Manifest 校验失败 |
| `3` | 输入音频不可读或格式不支持 |
| `4` | Steam Audio 初始化/渲染失败 |
| `5` | 输出写入失败 |

日志写入 stderr，成功时 stdout 只输出一行机器可读 JSON：

```json
{"ok":true,"sample_rate":48000,"channels":2,"duration_ms":105240,"sources":87}
```

### 6.2 后端 API

建议新增而不是立即替换旧接口：

```text
POST /v1/audio/spatial/render
Content-Type: multipart/form-data
```

字段：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `manifest` | JSON 字符串 | Render Manifest v1 |
| `assets` | 重复文件字段 | 对白、SFX、Ambience、BGM Blob |
| `profile` | `standard/balanced/immersive` | 继续复用现有 UI 档位 ID |
| `output_format` | `wav/mp3` | 最终格式 |

Manifest 的 `asset_filename` 只能引用本次上传文件的安全 basename，禁止绝对路径、`..`、URL 和符号链接。服务端必须重新生成内部文件名，不能直接信任上传文件名。

响应继续复用当前头部：

```text
Content-Type: audio/wav 或 audio/mpeg
Content-Disposition: attachment
X-Audio-Sample-Rate: 48000
X-Audio-Profile: balanced
X-Audio-Format: wav
X-Spatial-Engine: steam-audio
X-Spatial-Manifest-Version: 1.0
```

旧 `POST /v1/audio/export` 暂时保留作为 legacy/mastering 路径，直到新接口完成端到端回归。不要同一次导出先调用新 Steam 接口，再把结果送回旧 `balanced/immersive` Haas 滤镜。

### 6.3 输入标准化

进入 C++ 前由控制面使用 FFmpeg 统一：

- 点声源：48 kHz、mono、float32 或 renderer 明确支持的 PCM；
- BGM/需要保留的环境床：48 kHz stereo；
- 清除非法 metadata；
- 按 Manifest 执行 trim，但不得修改 IndexedDB 中的原始音频；
- 原始采样率可能来自 VoxCPM2、MOSS 48 kHz、Stable Audio 44.1 kHz、ACE-Step 48 kHz，不能假设一致。

### 7.2 环境变量

```text
STEAM_AUDIO_SDK_DIR
STEAM_AUDIO_RENDERER_BIN

STEAM_AUDIO_SCENE_PRESET_DIR

STEAM_AUDIO_RENDER_MAX_BYTES=2147483648
STEAM_AUDIO_RENDER_THREADS=4
STEAM_AUDIO_REFLECTIONS_ENABLED=0
STEAM_AUDIO_OCCLUSION_ENABLED=0
```

要求：

- `start.sh` 只校验 renderer 是否存在和可执行，不在启动时联网下载或编译；
- 8300 `/v1/health` 增加 `spatial_renderer` 诊断；
- renderer 不获取 `GPU_LOCK_FILE`；
- Windows 使用 `phonon.dll`，Linux 使用 `libphonon.so`，启动前验证动态库可解析；
- Phase 1 默认使用 Steam Audio built-in CPU 路径；Phase 2 再评估 Embree；不优先启用 Radeon Rays，避免与 4070 Ti Super 上的 TTS/SFX 模型争夺 GPU。

### 7.3 C++ Renderer 实现约束

1. 一个任务创建一个 `IPLContext`、`IPLHRTF`，每个同时活跃的点声源创建独立 `IPLBinauralEffect`。
2. 统一使用 48 kHz；frame size 可从 1024 起步，必须测试长音频内存和吞吐。
3. 静态声源可用 Nearest 或 Bilinear；所有移动声源必须默认 Bilinear。
4. 每个音频帧根据时间插值位置，转换为监听者坐标系中的方向。
5. Distance 不只改变音量：首版同时使用默认 distance attenuation 与 air absorption。
6. 最后一帧不足 frame size 时补零处理，输出后裁剪到期望时间线长度；不得像官方最小 sample 一样直接丢尾帧。
7. 所有 Steam Audio 对象使用 RAII 或严格逆序释放；异常路径也必须释放。
8. 混音前保留至少 6 dB headroom，禁止每源直接满幅相加；最终 loudness 交给现有 FFmpeg 双遍 loudnorm。
9. 输出不得出现 NaN/Inf，峰值超过安全范围时返回明确错误或执行受控限幅。
10. 首版只支持 WAV/规范化 PCM，不在 C++ 中承担 MP3 编码。

### 7.4 后端改造原则

- 复用当前 `StagedUpload`、大小限制、任务目录、超时终止、进程组清理和响应后清理模式；
- 新建 `SteamAudioRenderProcessor`，不要继续把所有职责塞进 `SpatialAudioProcessor`；
- 把当前 `SpatialAudioProcessor` 中 loudnorm/编码逻辑抽成可复用 `AudioMasteringProcessor`，或以最小改动复用其后半段；
- Steam 输出进入母带时只执行重采样兜底、限幅、loudnorm、编码，不再执行 `build_pre_master_filter("balanced")` 的 Haas/aecho；
- `standard` 继续支持无空间化导出；
- 新接口失败时不得静默回退到伪空间滤镜，应返回清晰错误，避免用户误以为听到的是 Steam Audio。

项目仍是静态页面，不创建新的 npm/Vite/Vue 子工程，不修改废弃的 `webUI/`。

### 8.2 工程数据兼容

建议先给 `dialogue` 和 `sfx_plan` 增加可选字段：

```json
{
  "spatial": {
    "mode": "point",
    "location": "front_left",
    "distance": "conversational",
    "movement": "static",
    "occlusion": "none",
    "spatial_blend": "medium",
    "source": "llm"
  }
}
```

兼容规则：

- 规范化必须写在 `js/project-storage.js`；
- 旧工程没有 `spatial` 时，运行时根据角色/SFX 生成安全默认值；
- 未完成端到端稳定前，可把 `spatial` 作为 Schema 4 的可选向后兼容字段，避免仅为实验字段立即升级工程版本；
- 如果后续把它变成必填协议，再执行 Schema 4 → 5 的正式迁移，并同时更新导入、导出、README、AGENTS 和回归样例；
- `audioUrl`、AbortController、渲染临时路径仍不得持久化；
- `asset_id` 必须从现有稳定 `audioAssetKey` 派生，不得把它拼成服务端路径。

### 8.3 LLM SpatialDirector

LLM 输入应包含：

- 场景摘要；
- 当前行及前后 1–2 行；
- 角色身份；
- `control_instruction` / emotion / intensity；
- `sfx_plan` 的中文与英文提示词；
- 上一条同角色的空间状态；
- DSL 枚举与严格 JSON Schema。

LLM 输出只允许语义字段。解析失败、枚举越界或上下文矛盾时，回退到脚本默认策略：

- 旁白 `front_center + conversational + static + subtle`；
- 普通角色使用稳定的前方左右锚点；
- SFX 从已有 prompt 的明确方向词生成；
- BGM `preserve_stereo`；
- 不允许回退为随机坐标。

### 8.4 预览与正式导出分离

Web Audio 无法替代 Steam Audio，但可以作为低延迟近似预览：

| 模式 | Web Audio 处理 | 后端 Steam Audio | 用途 |
| --- | --- | --- | --- |
| 标准预览 | 无 | 无 | 原始对比 |
| 近似空间预览 | StereoPanner/距离低通，可减少反射 | 无 | 编辑时快速确认方向与时间 |
| 正式 Steam 导出 | **不进入旧空间节点链** | 是 | 最终 WAV/MP3 |

UI 必须明确标注“近似预览”和“Steam Audio 正式导出”，避免用户把浏览器预览听感当作成品。

### 8.5 正式导出过程

1. 从 `scriptLines` 计算台词、停顿、SFX offset、BGM start/stop 的真实时间线。
2. 从 IndexedDB 读取每个对象的 Blob；不要先混成总线。
3. 调用 `spatial-compiler.js` 生成确定性 Render Manifest。
4. 只上传 Manifest 实际引用的资产，重复 `audioAssetKey` 去重。
5. 调用 `/v1/audio/spatial/render`。
6. 校验 `Content-Type`、非空 Blob、`X-Spatial-Engine: steam-audio`、采样率和格式。
7. 下载最终文件并正确回收对象 URL。
8. Abort 只取消浏览器等待；后端是否终止任务要以服务端取消协议为准，不能虚假显示“已停止 GPU/renderer”。

现有 `standard/balanced/immersive` ID 可以继续复用：

- `standard`：不使用 Steam Audio；
- `balanced`：保守 HRTF blend，旁白中心，关键 SFX 全空间化，Phase 2 使用较低反射参数；
- `immersive`：更强空间 blend、更明显的移动和反射，但仍限制旁白强度。

## 9. 分阶段实施顺序

### Phase 0：冻结基线与 A/B 素材

目标：在改造前保存可重复对比的输入与当前输出。

任务：

- 选取同一套 30–60 秒测试素材：旁白、普通角色、贴耳低语、身后脚步、门后人声、左侧敲门、走廊 Ambience、BGM；
- 保存所有 mono/stereo 原始输入；
- 导出当前 `standard/balanced/immersive` 三版；
- 记录响度、峰值、时长、采样率和生成命令；
- 测试素材不得包含未授权内容或提交真实用户工程数据。

验收：基线可一条命令重新生成，文件哈希或测量结果有记录。

### Phase 1：独立 Steam Audio CLI PoC

范围：只改 `TTS-and-VoiceDesign/model-audio/spatial_steam-audio/` 与相关脚本/测试。

能力：

- 单个 mono WAV → 48 kHz binaural stereo WAV；
- 静态前/后/左/右/上/下；
- `intimate/near/mid/far`；
- approaching/receding/左右穿越；
- 内置 HRTF；
- Bilinear 移动插值；
- CPU 渲染。

暂不做：房间几何、反射、遮挡、WebUI、LLM。

验收：

- Windows 11 x64 和项目主要 Linux 环境至少各有明确构建说明；
- 输入 48 kHz mono，输出严格 48 kHz stereo；
- 输出时长误差不超过 1 frame；
- 左右、前后、上下测试输出不相同；
- 同一输入与 Manifest 重复渲染结果确定一致；
- 无 NaN/Inf、无截断尾帧、退出码可诊断；
- 不启动 Python 模型、不占 GPU 锁。

### Phase 2：8300 控制面集成

范围：后端 API、任务治理、母带复用、健康检查。

能力：

- Manifest + 多资产上传；
- FFmpeg 输入标准化；
- 调用 CLI；
- 任务超时、进程组终止、缓存清理；
- Steam pre-master → loudnorm → WAV/MP3；
- 健康检查显示 SDK、renderer 和动态库状态。

验收：

- 无模型单元测试覆盖校验、路径穿越、资产缺失、重复 ID、上限、超时、失败清理；
- API 成功返回 `X-Spatial-Engine: steam-audio`；
- legacy `/v1/audio/export` 仍可用；
- Steam 路径不再叠加 Haas/aecho；
- 中途失败不残留大文件或孤儿进程。

### Phase 3：WebUI 对象级正式导出

范围：DSL、Compiler、客户端、IndexedDB 资产打包、近似预览分离。

能力：

- 对白和 SFX 保存可选语义空间计划；
- 对现有脚本一键生成默认计划；
- 正式导出上传对象而不是总线；
- BGM 保持稳定立体声；
- UI 展示当前引擎、空间档位和导出阶段。

验收：

- 旧 Schema 4 工程可导入、播放、导出；
- 完整工程导出/导入后空间计划不丢失；
- 正式 Steam 导出绕过旧 Web Audio 空间链路；
- 标准导出听感与现有 standard 基线无意外变化；
- Node 语法检查与 `node --test js/spatial-timeline.test.js` 通过，并增加 schema/compiler/client 测试；
- 浏览器手动回归覆盖单条、批量、取消、缺素材、大工程和后端错误。

### Phase 4：LLM SpatialDirector

范围：Prompt、严格 JSON、上下文连续性和回退规则。

验收：

- LLM 不输出 `x/y/z`、滤波器频率、射线数等底层 DSP 参数；
- 同一角色跨句位置稳定；
- 没有空间线索时不过度空间化；
- 关键事件能正确识别身后、楼上、门后、远近和移动；
- 返回非法 JSON 时工程仍可使用确定性默认计划；
- 本地 Qwen 与云端 OpenAI 兼容接口都走同一 Schema。

### Phase 5：Reflections / Reverb

能力：房间 preset、材质、反射、混响；优先使用少量通用几何场景，不由 LLM 生成任意三角网格。

建议先实现：

- `bedroom`；
- `narrow_corridor`；
- `stairwell`；
- `basement`；
- `warehouse`；
- `cave`；
- `outdoor_open`。

反射模拟 CPU 成本显著，先使用离线渲染和有限 preset；必要时使用 probe/baking，但不要在每句台词上重复构建完全相同的场景。

### Phase 6：Occlusion / Transmission

能力：门、墙、楼板遮挡与 3-band transmission。

优先案例：

- 木门后低语；
- 混凝土墙另一侧敲击；
- 楼上拖拽声；
- 走廊拐角脚步；
- 声源由遮挡区进入可见区。

验收不能只检查“音量变小”，还应检查材料导致的高频/中频变化以及遮挡状态过渡是否平滑。

## 11. 安全、性能与商业约束

### 11.1 安全

- 所有输入都视为不可信文件；
- 只接受明确的音频 MIME/扩展名，最终以实际解码结果为准；
- 禁止 Manifest 读取任意本地路径或远程 URL；
- subprocess 必须参数数组调用，禁止拼接 shell 字符串；
- 限制源数量、总时长、总大小、房间复杂度、射线数和反射时长；
- 临时目录按任务隔离并在响应结束后删除；
- API Key、模型权重、Steam SDK 本机路径和生成音频不得提交。

### 11.2 性能

- RTX 4070 Ti Super 16 GB 主要留给 TTS/SFX/BGM；Steam Phase 1 使用 CPU；
- 先测 30 秒、5 分钟、20 分钟三档；
- 不要一次把全部长音频解码到 RAM；生产 renderer 应逐帧或分块处理；
- 同一 HRTF 和 scene 在一个任务内复用；
- 同一房间 preset 的静态数据可缓存，但缓存必须带 Steam Audio 版本和 preset hash；
- Phase 5 反射应独立设置质量档位，避免 `immersive` 自动把射线数推到不可控范围。

### 11.3 许可证

- Steam Audio 仓库为 Apache-2.0，适合当前项目和后续商业化；
- 保留 LICENSE/NOTICE 要求，分发 DLL/SO 或派生源码时同步核对第三方依赖许可证；
- 自定义 SOFA HRTF、测试音频和房间 IR 可能有独立授权，不能因为 Steam Audio 是 Apache-2.0 就默认它们也可商用；
- 本文不是法律意见，正式商业发布前仍应对分发物做一次许可证清单审查。

## 14. 总体验收标准（Definition of Done）

- [ ] 本地 LLM 只生成 DSL，脚本确定性编译坐标和轨迹；
